# 0.6.0: the compose tool

> **0.5.0 comes first.** [next.md](next.md) holds its scope. This file
> lines up the work of the release after it. The rule on compatibility at
> the top of [next.md](next.md) holds here too: a change carries no
> compatibility path, and the changelog names it.

**0.6.0 gives a seat the `compose` tool.** The agent passes the tools that
it uses and short code. The code passes the result of one tool into the
next, runs calls in parallel, and returns one value to the model.
[Compose](../docs/compose.md) owns the contract. This file owns the work
and its evidence. [The backlog](backlog.md) holds everything else.

## The scope

**The release follows one compose call from the definition to the
model.**

```text
executor options -> describeExecutor appends compose -> catalog and guidance
                                                            |
            model -> compose({ uses, code }) -> approve -> evaluator
                                                            |
                         nested calls -> declared outputs -> ledger -> value
```

- **`compose({ uses, code })`** joins the tools of the definition. The
  model reads only the returned value, or the error and the ledger.
- **Declared outputs** give the code typed `details`. `defineTool` checks
  them at compile time, and `compose` checks them at every call.
- **`@ambionframework/evaluator`** holds `quickjsEvaluator` and
  `processEvaluator`. Both pass `evaluatorConformance`.
- **Pi, Claude, and Codex** host `compose` as one more definition tool.
- **One executor bug.** [B1](#b1-a-late-steer-on-claude-loses-its-answer)
  fixes a Claude steer that the core counts as read but the seat never
  answers.

## Decisions taken

- The tool is `compose`. One run is a compose call. The page never uses
  `composition`, which names the roster entry of the journal.
- `uses` is required. `compose` checks it, then asks `approve`, then
  evaluates the code.
- A declared tool gives its `details`. An undeclared tool gives its text.
- The room tools do not bind. A compose call computes a value, and the
  agent decides what to say.
- The code has no clock, no random source, no timer, and no I/O except
  through its bindings.
- A failed or cancelled compose call throws, and its message holds the
  ledger. A call that outlives the code keeps the result.
- The limits and the guidance live on the `compose` option.
- The live token comparison is evidence of the release (CP6). It gates no
  phase before phase 4.

## Out of scope

- **An evaluator for workerd.** A seat on `@ambionframework/cloudflare`
  has no `compose` option in 0.6.0.
- **Replay of a compose call from its trace.** The trace caps can cut a
  nested output.
- **Room tools in a compose call.** `say`, `schedule`, `seat`, `unseat`,
  `dismiss`, and `recall` stay direct calls.
- **Concurrent operations in one workspace.** Parallel calls of file tools
  still run one operation at a time. D9 holds concurrent operations.
- **A compose call inside a compose call.**

## Bugs

### B1. A late steer on Claude loses its answer

**Symptom.** A person sends a line while a Claude seat streams its final
answer. The trace records the `steer` step with `consumed: true`, and
`readThrough` moves past the line. The seat says nothing about the line,
unless its answer takes less than 5 seconds.

**Root cause.** Claude Code does not fold this line into the running turn.
It runs the line as a separate turn after the first `result`. That
`result` reports `queued_turn_count: 0`, so only the missing echo holds the
pass. The executor parks the result behind `ECHO_GRACE`, 5 seconds
([`executor.ts`](../packages/claude/src/executor.ts), `answered` and
`settleWith`). The echo of the line arrives when the second turn sends its
request, and `echoed` calls `read`. The echo does not restart the timer.
At 5 seconds the pass settles with the first result. The record holds
nothing unread, so the driver releases the activation, and `close` stops
the turn that answers the line.

**Reproduction on the real binary.** Claude Code 2.1.284, the binary of
SDK 0.3.284, ran against a local scripted Messages API. An
`ActivationState` over `createClaudeOpener` ran one pass. The first turn
streamed for 3 seconds, and the line landed 1.2 seconds after its request.
The second turn streamed for 8 seconds. Times are in milliseconds.

```text
  1276 request 1
  2476 steer, seq 2
  4285 result 1, queued_turn_count 0
  4401 request 2, and the echo of the line
  9372 the pass settles: readThrough 2, steer consumed: true, shouldRefresh(2) false
 12417 turn 2 ends, after the pass
```

The same probe showed two facts that hold. With partial messages on, the
echo of a message arrives as its request goes out. A line that lands
during a tool call joins the next `tool_result` as a system reminder, and
its echo arrives with that request.

**The fake executable cannot catch it.** The fake always reports
`queued_turn_count: 0`. It echoes a message when the message arrives, and
it runs the next turn at once. A message that lands during the last turn
therefore has its echo before the `result`
([`claude-executable.mjs`](../packages/claude/test/fake/claude-executable.mjs)).

**Fix direction.** An echo that arrives while a result waits on the grace
timer means that another turn runs. The executor cancels the timer, and the
pass settles on the `result` of that turn. The grace timer stays for a
result whose echo never comes.

**Evidence:**

- The fake gains a step that holds a message until the turn ends, then
  echoes it with the request of the next turn, after the `result`.
- A test in `packages/claude/test/steer-echo.test.ts` sends a line during
  the final text of a turn whose next turn takes longer than
  `ECHO_GRACE`. The pass settles on the second result, and the say of
  that turn commits after the line.
- The live steer test gains one case that steers during the final answer.
  It runs once, when a person asks for release evidence.
