# 0.9.0: Unattended rooms

**0.9.0 lets a person leave a room overnight and find it running.** A
room that runs unattended keeps its clock through an outage, keeps its
prompt in a window, says when it fails, and keeps its processes through a
clean stop. Each item closes a risk that the robustness evaluation of
2026-10-05 reproduced or read in the code. [1.0.0](1.0.0.md) holds the
road.

**Evidence:**

- On the scripted fake clock, an outage of 10 minutes ends no chain of
  scheduled says. The chain continues when the provider answers.
- A run of 30 self-scheduled cycles keeps the rendered prompt within the
  window. A closed exchange with no spoken message renders as one line,
  and `recall` reads it.
- A throw in `decide`, a throw in an opener, and a failed write in
  `reconcile` each emit one `error` notification and leave the room with
  an alarm. No rejection is unhandled.
- Each failure path in the list of [UR3](#the-items) emits its event once.
- A clean stop of the workbench leaves a running controller running. The
  next start adopts it. One command cancels every running process of a
  room.
- A wall clock that jumps forward one hour spends no attempt of a running
  lease.
- `pnpm rule:check` passes on each rules file that UR1 and UR5 change.
- The executor conformance suite checks, for Pi, Claude, and Codex, one
  `session` step with the model, and one `usage` step for each model
  request.
- A scripted workbench room exports to a local Phoenix container. Phoenix
  shows one session for each exchange and one trace for each activation.
- A Phoenix that does not answer costs the room nothing, and the workbench
  reports the failure once.

## The items

**UR1. Retries that survive an outage.** An activation makes 3 attempts
at 30 s and 60 s, and then the room records `abandoned`. The room consumes
a returned say when it posts it, so a chain of scheduled says ends for
good after an outage of about 90 s. A person's question closes
`exhausted` after the same outage. Code: `room/scheduled.ts`,
`room/reconcile.ts`, the `activation` limits in `host/runtime.ts`.

- About 8 attempts, with exponential backoff that stops growing at 1 hour.
  The next attempt still derives from the record, so no journal body
  changes.
- `docs/durability.md` states the window of time that the defaults cover.

**UR2. A bounded prompt for an ambient room.** `limits.context.messages`
is `Infinity` by default, and an exchange with no person owes no summary.
The cost of each activation grows with the record. A provider then
refuses the prompt with a 400, which the room reads as permanent. Code:
`host/runtime.ts`, `room/view.ts`, `owesSummary` in
`room/rules.verified.ts`.

- A finite default for `limits.context.messages`. `capOf` already keeps
  the open exchange whole.
- A closed exchange with no spoken message renders as one line, and
  `recall` still reads it.

**UR3. Failures that a host sees.** A failure at the level of the room
emits nothing today. `reconcile` in `room-run/control.ts` ends in a catch
that drops the error. `decide` runs before the `try` in `onePass`, so a
throw arms no alarm. `runner.ts` builds the activation state before its
`try`, so an opener that throws produces an unhandled rejection on each
resend, and the default Node setting ends the host.

- `decide` runs inside the `try` of `onePass`, and the catch emits the
  `error` notification before it arms the alarm again.
- A failed write in `reconcile` emits `error` once before the room arms
  the alarm again. The catch that drops the error goes.
- The runner builds the activation state inside its `try`. An opener or
  `trace.open` that throws ends the activation as permanent, through the
  release, `abandoned`, and the event.
- The `error` notification takes an optional `seat` and `activation`,
  since a failure of the room has neither. The export snapshot changes.
- `docs/deployment.md` lists the events that a host must subscribe to:
  `error`, `port_error`, `exchange_closed` with `exhausted`, and
  `abandoned`. A test runs each failure path and finds its event once.

**UR4. Processes that outlive a clean stop, and one stop for a room.**
`dispose()` cancels every running process, so a clean quit of the
workbench stops the controllers and the loggers of the night. A crash
leaves them running. Code: `packages/workspace/src/workspace.ts`,
`examples/workbench/src/rooms.ts`.

- A `dispose` option that leaves running processes for the next run to
  adopt. The workbench uses it at a clean stop.
- `workspace.processes.cancel({ room })` cancels every running process
  that a room started, each with its grace.
- The workbench binds one key to that cancel. The interlock of the device
  stays the last guard.

**UR5. Hosts that sleep.** Timers run on the monotonic clock, and the room
decides on the wall clock. After a laptop sleeps, alarms fire late, and
each running lease expires at its next renewal and spends an attempt. The
default alarm in `host/clock.ts` is `unref`, so a host that awaits nothing
exits.

- A lease that expires across a jump of the wall clock spends no attempt.
- The core alarm stays `unref`. The workbench keeps the event loop alive
  while a room runs, and `docs/deployment.md` keeps the rule for other
  hosts.
- On macOS, the workbench holds a sleep assertion while a process runs.

**UR6. The trace contract, and Phoenix in the workbench.** A person who
leaves a room overnight reads in the morning how each activation went.
The trace hooks of [0.8.0](0.8.0.md) give the facts, and the workbench
sends them to Phoenix.

- The executor conformance suite asserts the steps that each executor
  must record: `session`, one `usage` for each request, and `input` under
  the full policy.
- A page `docs/traces.md` states the steps, their order, the policy, the
  limits, and the mapping of the steps to a span tree. The page names no
  backend as the default, and it states that the full policy copies
  secrets to the logger.
- `examples/workbench` takes a Phoenix URL and sends each activation as
  OpenInference spans over OTLP. The kernel has no OpenTelemetry
  dependency. The design is `observability/phoenix-design.md` in the
  project files.
